SENVORYN CORE CONTRACT SPECIFICATION — LOCAL VALIDATION REPORT
Date: 2026-10-22
Specification: SENVORYN Core Contract Specification v0.1.0
Baseline constitution: v0.6.0

Validation environment
- Python: 3.12.10
- jsonschema: 4.26.0
- Rust: 1.98.0 (stable), rustc and cargo
- Host architecture: x86_64
- Third-party Rust dependencies: 0

Checks performed
- Python contract tests: 124 passed, 0 failed.
- Rust workspace tests: 144 passed, 0 failed.
- Shared conformance vectors: 49 decision cases and 11 attenuation cases executed by the
  Python reference model and by the Rust implementation. Both suites agree on every
  decision status and every reason code. The two suites are the mechanism that keeps the
  prototype and the implementation from becoming two authorities on the same question.
- Change Capsule vectors: 42 cases executed by the Rust implementation AND by the Python
  reference model, covering the registry's authority over risk and approval
  requirements, the digest binding of the decision and its approvals, the version the
  decision was made against, the status the decision carried, the plan the request named,
  the version and epoch checks, the preconditions, the budget, the mandatory
  postconditions, the durability of the evidence, the compensation planner, every injected
  fault, and the five cases in which the world moves under the transaction. Both
  implementations reach the state each case names, and CI fails on a disagreement.
- Change Capsule validity window: the clock is read before every step, the simulated
  clock advances by each step's own timeout, a clock that moves backwards ends the
  transaction rather than being believed, and a capsule cannot be executed before it
  was issued. Five of the new controls are broken in turn by the mutation gate: the
  clock's monotonicity, the issue time, the per-step window check, the recovery
  material's integrity at the precheck and at the commit, and the compensation's own
  check that the material is usable.
- Change Capsule fault model: eight fault kinds crossed with thirteen fault points, 104
  combinations. Three of the kinds change the world rather than interrupting the
  transaction — a full disk, a clock that rolls back, and a recovery artefact that
  turns out to be corrupt — and the transaction has to find each of them for itself.
- Change Capsule fault model: every fault point crossed with every fault kind. The
  property asserted is that a fault never produces a COMMITTED report, and it holds for
  all 104 combinations. The property test also asserts that each injected fault
  actually fired, so a fault at a point the transaction never reaches cannot pass
  quietly.
- Change Capsule reference model: a second implementation of the capsule executor, written
  in Python from the contract rather than from the Rust. It is held to the same vector
  file, and the two agree on all 42 cases. Writing it found three defects in the Rust
  implementation that no test had caught: the registry's merge rule kept the more
  reversible of two conflicting rules, the timestamp parser refused every timestamp with
  fractional seconds, and the timestamp parser rolled a date that does not exist into the
  next month. All three are fixed and pinned by a test in each implementation.
- Denial-code registry: 34 codes, unique, each with a class and a default status. Every
  code an implementation can produce is in the registry, and that direction is checked by
  a test on both sides. The other direction is checked too: 32 of the 34 codes are
  produced by a shared vector, and the two that are not are named by the test that checks
  it. UNSUPPORTED_CRITICAL_SCHEMA names the transport's refusal of a document whose
  schema this node does not support, which is a refusal and not a decision, because the
  request never existed; ANTI_ROLLBACK_VIOLATION names the updater's refusal of a
  downgrade, and there is no updater. A code added to the registry without a case that
  produces it fails the test in both implementations, and the failure asks the author to
  say which of the two kinds of code it is.
- A future policy epoch is deferred, not denied. DEFER was in the specification, the
  schema, the decision-status enum and the capsule executor's refusal of anything that
  grants no authority, and no rule produced it. A request naming a policy epoch this
  node has not reached is now deferred with the reason code
  POLICY_EPOCH_NOT_YET_IN_FORCE, provided the operation is non-destructive: the registry
  in force declares it reversible and gives it no external effect. The deferral names the
  epoch it waits for, carries no capability scope, grants nothing, and does not outlive
  the request it defers, because the freshness gate runs before the epoch gate. A stale
  epoch is still denied, an operation the registry does not know is still denied, and the
  registry's own epoch binding and validity window are settled before the request's epoch
  is read at all, because a decision may not be made under a policy that is not in force.
  Six shared cases carry the rule, and each condition of it has a case that only it can
  refuse: the future epoch, the stale epoch, an irreversible operation, an operation with
  an external effect, an operation the registry does not know, and a request that expired
  before the deferral could be made. Thirteen controls are broken in turn by the mutation
  gate, seven in the Rust oracle and six in the Python reference model, so that neither
  implementation's version of the rule is the only one being tested.
- A quarantined principal is quarantined, not merely denied. QUARANTINE was in the
  specification, the schema, the decision-status enum and the capsule executor's refusal of
  anything that grants no authority, and no rule produced it, so the capsule harness had to
  refuse to write a decision under that name rather than write a denial and call it a
  quarantine. A request from a principal this node holds under quarantine is now
  quarantined with the reason code PRINCIPAL_QUARANTINED. The isolation is a state of the
  subject and not a penalty for an error, so it is settled at the identity gate, before the
  resource is resolved and before the capability is examined: a quarantined principal learns
  that it is quarantined and nothing else, and the request's own freshness is not judged
  either. A quarantined principal is still a known principal - it is held apart, not let go -
  so the node can acknowledge it and say why, and the decision names the principal it holds,
  which the record publishes as the next step: the isolation is lifted by a policy decision
  and not by a clock. No other failure falls back to a quarantine, and a principal the node
  has never heard of is still refused as unknown, which is why the check sits after the
  known-principal check rather than before it. Three shared cases carry the rule, and each
  condition of it has a case that only it can refuse: the quarantined principal, the
  quarantined principal whose request has expired, and the principal the node does not know
  even though the quarantine set names it. Thirteen controls are broken in turn by the
  mutation gate, seven in the Rust oracle and six in the Python reference model, so that
  neither implementation's version of the rule is the only one being tested. The capsule
  vector CC-042 shows the executor refusing a quarantined decision like any other decision
  that grants no authority.
- The policy request form is closed: a document carrying a field the form does not define
  is refused, at the top level and inside the budget, because a field this node cannot
  account for may be a field a newer sender expects this node to enforce. The reader
  enforces the form and nothing else. Nine of its controls are broken in turn by the
  mutation gate: the closed field set, the closed budget, the object check, the schema
  check, the missing field, the empty field, the negative number, the malformed risk
  claim, and the reader's duty to keep the value it read.
- The request boundary is fuzzed: a corpus of policy requests is mutated in a reproducible
  way, and the harness asserts that the reader never panics, that a request which was
  read says exactly what the document said, and that the same document is read the same
  way twice. The policy request form and the wire envelope the schema describes are
  different documents, and the transport that converts one into the other does not exist
  yet; the drift between them is recorded in ADR-019 rather than implied.
- The decision names the version it was made against: the authorization carries the
  version of the target the decision was made against, and the executor refuses a
  decision that names none — it was made before the resource was resolved, so it was
  made about a name rather than an object — or names another. The digest binding answers
  "is this the plan I judged?" and the version binding answers "was the object in the
  state I judged it in?". The canonical identifier is not compared, because the
  capsule's own target name may be an alias. Four controls are broken in turn by the
  mutation gate, two in the Rust executor and two in the Python reference model: the
  version comparison and the refusal of a decision that names no version.
- The resolution boundary: a resolved resource is a canonical identifier, a canonical
  type and a version. The canonical identity — never the caller's own strings — governs
  the capability gate, the risk gate, and the record that authorises the effect. A
  caller's type claim is checked rather than obeyed, so a request that misdescribes its
  own target is refused with RESOURCE_TYPE_MISMATCH rather than corrected, and an
  alias resolves to the object it means and still has to match a grant over that
  object. Five controls are broken in turn by the mutation gate, in the Rust oracle and
  in the Python reference model: the resolution itself, the type cross-check, the
  canonical identifier in the capability gate, the canonical type in the capability
  gate, and the canonical type in the risk gate.
- Change Capsule timestamp boundary: the strict-UTC parser's guards — the form, the zone
  marker, the fraction, the date, the leap year, the time and the year — are each broken
  in turn by the mutation gate, in the Rust executor and in the Python reference model.
  A case that two guards could refuse is not used, because a guard that is only ever
  reached together with another one can be removed and nothing would change.
- JSON Schema Draft 2020-12 structural checks: 14 schemas passed.
- JSON syntax checks: 26 JSON documents parsed. The count excludes build output, so it
  does not depend on whether the workspace has been built.
- Canonical JSON profile SCP-CJSON-0001: 40 conformance tests over the profile's clauses,
  plus a deterministic fuzz harness over a seed corpus (132000 mutated inputs, no panic,
  no encoding disagreement).
- Property tests over a seeded generator: attenuation never broadens a capability, the
  evaluator is deterministic, the evaluator mutates nothing it is given, and a decision
  that does not permit grants no authority.
- Operation registry sample: validated against its schema; sample is explicitly unsigned
  and is not production policy.
- Change Capsule sample: validated against its schema; a precondition without an
  expected value is rejected by the schema and by the Rust reader.
- Mutation gate: 174 controls broken in turn, each requiring a named test to go red
  because of that break. 174 killed, 0 survived, 0 invalid. The gate runs tests in Rust
  and in Python, and clears the Python bytecode cache before each run, because a cached
  bytecode file can shadow a mutated source.
- Decision-record boundary: the policy layer writes the decision record and the capsule
  executor reads it, through a closed reader that refuses a record carrying a field the
  record does not define and a record that claims an effect was performed. The request
  may name the plan it asks to run, the record carries that plan, and the executor reads
  the plan, the version and the status out of the record: a decision that refused a
  request authorises nothing, and a decision that names no plan authorises no plan. The
  capsule's vector harness writes the record through the policy layer's own writer and
  reads it through the policy layer's own reader, so the two ends cannot drift apart.

Limitations
This report validates a documentation/specification package, a pure reference policy model,
a pure decision function, and a transaction simulator. It does not validate an OS kernel,
hardware isolation, cryptographic implementation, production policy enforcement, secure
boot, real installation/recovery, or application compatibility.

The Rust crate `senvoryn-scp` is a decision function, not an SCP. It verifies no
signature, resolves no resource against a filesystem, keeps no trust store, and writes no
audit record. The development tool `senvoryn-cli` is a driver for that function and says
so in its own help. Neither may be deployed as a security boundary.

The Rust crate `senvoryn-capsule` is a simulator, not an executor. It drives the Change
Capsule state machine against a simulated environment and performs no effect of any
kind. The Python reference model `reference/capsule_reference.py` is a simulator too.
The compensation they model is not exercised against real storage, so nothing in this
repository shows that a real system can be rolled back.

Two implementations of one specification is a strong check and not a proof. Both
implementations read the same vector file, and whoever writes that file decides what
"right" means. Neither implementation is an independent reviewer.

The resolution boundary is specified but not finished. The environment's resolution
table is supplied to the oracle; nothing in this repository resolves a name against a
filesystem, decides which resource types need a richer identity than an identifier, a
type and a version, or says who may define an alias and how one is revoked. The plan
and the version the executor checks now come from the decision record the policy layer
wrote, but the approvals are still passed to the executor beside it, because the policy
layer is given the approval's digest and not the approval; the record's validity window
and its capability scope are read and not compared; and the record is not signed, so it
is trusted because the policy layer wrote it inside the trust boundary and not because
it is proved.

The Operation Registry used by the tests is the unsigned sample. Capability provenance is
stated by the caller and checked for consistency, not proven: there is no signature
verification in either implementation. No artifact in this repository is signed.
