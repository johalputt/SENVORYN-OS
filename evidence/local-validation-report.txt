SENVORYN CORE CONTRACT SPECIFICATION — LOCAL VALIDATION REPORT
Date: 2026-10-22
Specification: SENVORYN Core Contract Specification v0.1.0
Baseline constitution: v0.6.0

Validation environment
- Python: 3.12.10
- jsonschema: 4.26.0
- Rust: 1.98.0 (stable), rustc and cargo
- Host architecture: x86_64
- Third-party Rust dependencies: 0

Checks performed
- Python contract tests: 105 passed, 0 failed.
- Rust workspace tests: 123 passed, 0 failed.
- Shared conformance vectors: 40 decision cases and 11 attenuation cases executed by the
  Python reference model and by the Rust implementation. Both suites agree on every
  decision status and every reason code. The two suites are the mechanism that keeps the
  prototype and the implementation from becoming two authorities on the same question.
- Change Capsule vectors: 36 cases executed by the Rust implementation AND by the Python
  reference model, covering the registry's authority over risk and approval
  requirements, the digest binding of the decision and its approvals, the version and
  epoch checks, the preconditions, the budget, the mandatory postconditions, the
  durability of the evidence, the compensation planner, every injected fault, and the
  five cases in which the world moves under the transaction. Both implementations reach
  the state each case names, and CI fails on a disagreement.
- Change Capsule validity window: the clock is read before every step, the simulated
  clock advances by each step's own timeout, a clock that moves backwards ends the
  transaction rather than being believed, and a capsule cannot be executed before it
  was issued. Five of the new controls are broken in turn by the mutation gate: the
  clock's monotonicity, the issue time, the per-step window check, the recovery
  material's integrity at the precheck and at the commit, and the compensation's own
  check that the material is usable.
- Change Capsule fault model: eight fault kinds crossed with thirteen fault points, 104
  combinations. Three of the kinds change the world rather than interrupting the
  transaction — a full disk, a clock that rolls back, and a recovery artefact that
  turns out to be corrupt — and the transaction has to find each of them for itself.
- Change Capsule fault model: every fault point crossed with every fault kind. The
  property asserted is that a fault never produces a COMMITTED report, and it holds for
  all 104 combinations. The property test also asserts that each injected fault
  actually fired, so a fault at a point the transaction never reaches cannot pass
  quietly.
- Change Capsule reference model: a second implementation of the capsule executor, written
  in Python from the contract rather than from the Rust. It is held to the same vector
  file, and the two agree on all 36 cases. Writing it found three defects in the Rust
  implementation that no test had caught: the registry's merge rule kept the more
  reversible of two conflicting rules, the timestamp parser refused every timestamp with
  fractional seconds, and the timestamp parser rolled a date that does not exist into the
  next month. All three are fixed and pinned by a test in each implementation.
- Denial-code registry: 32 codes, unique, each with a class and a default status. Every
  code is produced by at least one implementation and every code an implementation can
  produce is in the registry; both directions are checked by tests on both sides.
- The resolution boundary: a resolved resource is a canonical identifier, a canonical
  type and a version. The canonical identity — never the caller's own strings — governs
  the capability gate, the risk gate, and the record that authorises the effect. A
  caller's type claim is checked rather than obeyed, so a request that misdescribes its
  own target is refused with RESOURCE_TYPE_MISMATCH rather than corrected, and an
  alias resolves to the object it means and still has to match a grant over that
  object. Five controls are broken in turn by the mutation gate, in the Rust oracle and
  in the Python reference model: the resolution itself, the type cross-check, the
  canonical identifier in the capability gate, the canonical type in the capability
  gate, and the canonical type in the risk gate.
- Change Capsule timestamp boundary: the strict-UTC parser's guards — the form, the zone
  marker, the fraction, the date, the leap year, the time and the year — are each broken
  in turn by the mutation gate, in the Rust executor and in the Python reference model.
  A case that two guards could refuse is not used, because a guard that is only ever
  reached together with another one can be removed and nothing would change.
- JSON Schema Draft 2020-12 structural checks: 14 schemas passed.
- JSON syntax checks: 26 JSON documents parsed. The count excludes build output, so it
  does not depend on whether the workspace has been built.
- Canonical JSON profile SCP-CJSON-0001: 40 conformance tests over the profile's clauses,
  plus a deterministic fuzz harness over a seed corpus (132000 mutated inputs, no panic,
  no encoding disagreement).
- Property tests over a seeded generator: attenuation never broadens a capability, the
  evaluator is deterministic, the evaluator mutates nothing it is given, and a decision
  that does not permit grants no authority.
- Operation registry sample: validated against its schema; sample is explicitly unsigned
  and is not production policy.
- Change Capsule sample: validated against its schema; a precondition without an
  expected value is rejected by the schema and by the Rust reader.
- Mutation gate: 126 controls broken in turn, each requiring a named test to go red
  because of that break. 126 killed, 0 survived, 0 invalid. The gate runs tests in Rust
  and in Python, and clears the Python bytecode cache before each run, because a cached
  bytecode file can shadow a mutated source.

Limitations
This report validates a documentation/specification package, a pure reference policy model,
a pure decision function, and a transaction simulator. It does not validate an OS kernel,
hardware isolation, cryptographic implementation, production policy enforcement, secure
boot, real installation/recovery, or application compatibility.

The Rust crate `senvoryn-scp` is a decision function, not an SCP. It verifies no
signature, resolves no resource against a filesystem, keeps no trust store, and writes no
audit record. The development tool `senvoryn-cli` is a driver for that function and says
so in its own help. Neither may be deployed as a security boundary.

The Rust crate `senvoryn-capsule` is a simulator, not an executor. It drives the Change
Capsule state machine against a simulated environment and performs no effect of any
kind. The Python reference model `reference/capsule_reference.py` is a simulator too.
The compensation they model is not exercised against real storage, so nothing in this
repository shows that a real system can be rolled back.

Two implementations of one specification is a strong check and not a proof. Both
implementations read the same vector file, and whoever writes that file decides what
"right" means. Neither implementation is an independent reviewer.

The resolution boundary is specified but not finished. The environment's resolution
table is supplied to the oracle; nothing in this repository resolves a name against a
filesystem, decides which resource types need a richer identity than an identifier, a
type and a version, or says who may define an alias and how one is revoked. The
executor does not yet recheck the resolved version before it acts, so the record's
version is an anchor that nothing compares against yet.

The Operation Registry used by the tests is the unsigned sample. Capability provenance is
stated by the caller and checked for consistency, not proven: there is no signature
verification in either implementation. No artifact in this repository is signed.
